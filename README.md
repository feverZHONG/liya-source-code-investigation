# 外部项目调查 · Source Code Investigation

> 调查一个**不是你写的**项目：开源项目、游戏私服、APK 魔改包、只有二进制的 MOD——
> 弄清它到底是什么、怎么实现、改了哪儿、数据规模多大、作者是谁。

## 什么时候用它

| 输入长这样 | 走它 |
|:--|:--|
| 「这个项目怎么样 / 靠不靠谱 / 有没有风险」 | ✅ |
| 要弄清「README 说的」和「实际做的」对不对得上 | ✅ |
| 事件或档案需要对一个仓库做技术深挖 | ✅ |
| 只有编译产物、没有源码（`.dll` / `.exe` / 游戏 MOD） | ✅ 纯 Python 反汇编（见下） |
| 想从仓库里**拿组件来用** | ❌ 那是提取视角，本文是调查／审计视角 |

**一句话分界**：这里的目标产物是**分析结论**，不是可复用代码。

## 方法（六步）

1. **仓库状态侦察** —— 先走 API（语言／许可／活跃度／有没有编译好的 release／目录树）；
   只有「判断有没有二进制可拆」和「判断死活（pushed_at）」两种情况值得先查，急查直接 clone
2. **clone 到缓存目录**（源码不入 git）；国内 clone 超时走 tarball 方案
3. **逐文件读** —— 几百行的小文件全读（入口／协议／路由都在小文件里），几万行的大文件先读结构定义再 grep 挑段
4. **数据规模实测** —— 不信 README 声称的数字，用正则数结构体验证；仓库级资源盘点要**按 sha 去重**（同一套资源常在两处各存一份，原始计数会翻倍），且「文件数 → 去重数」两个数都给
5. **README 里的路径 = 身份链线索** —— 写死的本地开发路径常泄露项目真名与作者环境，拿去和别处截图／日志交叉比对
6. **对照旧判断** —— 新证据推翻旧定性的，档案里写明「哪条判断被修正」，不能静默改

## 最硬的一条铁律

**完成度 ≠ 作者懂机制。** 分析 AI 辅助项目（作者自述用 Codex／GPT／Copilot）时，第一刀就是分清「生成的」和「人写的」：
代码完成度高只证明 AI 写得多、数据管线成熟，**证明不了人懂多少机制**——「功能全 → 作者理解深」这条推理链是断的。
先查生成痕迹（文件头 `Generated by`／`Do not edit`、大批量常量表），再找人写痕迹（引用内部类名、架构取舍注释、协议逆向、注入点选择）。

## 工具

`scripts/ildump.py` —— 纯 Python 反汇编 .NET 二进制（`dnfile` + `dncil`，不用装 .NET／mono、不需要 root）。
权重表、触发链这类**不在配置文件里**的机制全在 IL 的立即数里。

```bash
uv venv .venv-dotnet --python 3.13
uv pip install --python .venv-dotnet/bin/python dnfile dncil
.venv-dotnet/bin/python scripts/ildump.py <dll> list "关键词"   # 列方法
.venv-dotnet/bin/python scripts/ildump.py <dll> dis  "<类型>.<方法>"  # 反汇编
```

配方与八个坑（含编译器生成的闭包怎么拆、权重是相对值不是百分比）见 `references/dotnet-il-dump.md`。

## 怎么用

把它放进你的 skills 目录（目录名用 `source-code-investigation`）：

```bash
git clone https://github.com/feverZHONG/liya-source-code-investigation.git <你的数据根>/skills/source-code-investigation
```
