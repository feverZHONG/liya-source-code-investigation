## 工作流

### ① 仓库状态侦察（可选，急查直接 clone）

```bash
curl -s "https://api.github.com/repos/{owner}/{repo}"          # 语言/许可/活跃度/pushed_at
curl -s "https://api.github.com/repos/{owner}/{repo}/releases" # 有没有编译好的二进制可拆
curl -s "https://api.github.com/repos/{owner}/{repo}/git/trees/main?recursive=1"
```

**减法（2026-08-12）：API 侦察轮可省——clone 后 `git log` + README + 目录树全有。** 只有两个场景值得先查 API：①判断有没有 release 二进制（有就不 clone 直接拆包）；②pushed_at 距今 >10 天判断死活。

**第三个 API-first 场景（2026-09-12）：评估一个项目「能不能用」（尤其 CLI 可用程度）——不 clone、不下载、不执行，全程 GitHub API + `raw.githubusercontent` 单文件抓取就够。** 只读场景（群聊）本来就不允许落盘跑二进制，静态结论照样能下得很硬。配方 + 评估维度清单见 `references/cli-usability-audit.md`。

**镜像站的 release 常滞后——判版本以主站为准（2026-09 实测）**：国内项目常在 Gitee 建仓、GitHub 发版，Gitee 的 releases 可能停在一两年前（实测一处 Gitee 最新 v1.5.5，而 GitHub 已 v1.9.3，README 的 release 徽章指向 GitHub）。评估「能不能拿到可用版本」时两边都查；给用户的下载指路要指名主站，否则他下到的是旧包——这类落差要写进结论，不能只报一句「有预编译包」。

**第四个 API-first 场景：「这个仓库是什么、怎么实现的，了解一下」。** 同样不必 clone——`repos/{o}/{r}` 拿 `created_at/pushed_at/stars/forks/license/size`，`git/trees/main?recursive=1` 拿文件清单，`readme`（`Accept: application/vnd.github.raw`）拿全文，再照 README 的「文件结构」表**逐文件抓 raw**读实现（`raw.githubusercontent.com/<o>/<r>/main/<path>`，批量换 jsdelivr）。两条判据：① **README 的描述必须去源码复核**——它说「单模型／端到端」就翻训练脚本看是否真共享一个 policy＋优化器，说「只用画面」就翻观测构造看奖励/胜负信号是否读内存；② **`created_at` 与相关公告/视频同日 ⇒ 当天建仓的「发布会仓库」**，报「做了多久／多少人用」时别按经营已久的项目写（配套看 commit 数、star/fork/issue 量级、有无 release）。源码只读不落库时结论一样能下硬：把「声称 vs 实际」写成两列对账，比转述 README 有用。

### ② clone 到 cache/（不入 git）

```bash
git clone --depth 1 https://github.com/{owner}/{repo}.git cache/{调查目录}/
```

- 源码 clone 必须放 `cache/`，结论写 `workspace/records/`，源码不入 git
- 国内 clone 超时 → **tarball 方案**（走 `api.github.com`，连通性最好，1–3MB 的包基本 30s 内拉完）：
  ```bash
  curl -sL "https://api.github.com/repos/{owner}/{repo}/tarball" -o x.tar.gz && tar xzf x.tar.gz
  # 解压出来目录名是一串 sha，记得 mv 成正式名；只取包内几个文件时加 --wildcards
  ```

### ③ 逐文件读（小全读、大挑段）

- 几百行的小文件（lib.rs/http.rs/proto.rs 类）**全读**——入口/协议/路由都在小文件里
- 几万行的大文件（data.rs 类）先读头部结构定义 + grep/正则挑关键段

### ④ 数据规模实测（验证 README 声称的数字）

README 说「683 话题/287 动态」？用正则数结构体验证，别轻信描述：

```python
import re
src = open('src/data.rs', encoding='utf-8').read()
for name in ['PHONE_LETTERS', 'PHONE_BBS']:
    m = re.search(r'pub const '+name+r':[^=]+= &\[(.*?)\];', src, re.S)
    print(name, '=>', len(re.findall(r'PhoneTopic\s*\{[^}]*\}', m.group(1))))
```

对上 = README 可信；对不上 = 描述夸大，记入档案。

**仓库级资源盘点（tree + sha 去重，2026-09 实测）**：被问「这仓库有多少美术资源／多少张图／多少个模型」时，**文件数不是答案，唯一 sha 才是**——同一套资源常在两处各存一份（成品目录 + 关卡目录），原始计数会翻倍。

```bash
curl -s "https://api.github.com/repos/{owner}/{repo}/git/trees/main?recursive=1" -o /tmp/tree.json
python3 - <<'EOF'
import json, collections, re
d = json.load(open('/tmp/tree.json'))
blobs = [t for t in d["tree"] if t["type"] == "blob"]
cnt, uniq = collections.Counter(), collections.defaultdict(set)
for b in blobs:
    m = re.search(r'\.([A-Za-z0-9]+)$', b["path"])
    e = m.group(1).lower() if m else "noext"
    cnt[e] += 1; uniq[e].add(b["sha"])
for e in sorted(cnt, key=lambda x: -cnt[x])[:10]:
    print(f"{e:<12}{cnt[e]:>7}{len(uniq[e]):>10}")
EOF
```

两条纪律：① 汇报时**「文件数 → 去重数」两个数都给**（用户要的是能用多少）；② 返回里 `truncated: true` 表示树被截断（大仓库），此时计数是下界，别当总数报。要数「动作/动画」这类内部条目，就按去重后的路径表批量取文件再解析，别抽样外推。

**取一批文件走 jsdelivr，别用 raw.githubusercontent（2026-09 实测）**：同一批 51 个文件，`raw.githubusercontent.com` 十几秒只下到 1 个（其余超时），`cdn.jsdelivr.net/gh/<owner>/<repo>@<branch>/<path>` 配 `xargs -P 8` 十秒全下完：

```bash
cat list.txt | sed 's|^|https://cdn.jsdelivr.net/gh/OWNER/REPO@main/|' > urls.txt
cat urls.txt | xargs -P 8 -n 1 sh -c 'u="$0"; f=$(echo "$u" | sed "s|.*@main/||; s|/|__|g"); curl -sL --max-time 35 -o "/tmp/dl/$f" "$u"'
```

落盘名把 `/` 换成 `__` 平铺，免得建目录；**收文件用 `glob('/tmp/dl/*')` 而不是 `*.json`**——`.spinejson` 这类复合后缀会被 `*.json` 漏掉（实测白跑一轮）。

### ⑤ README 路径 / 提交元数据 = 身份链线索

源码/README 里的**本地开发路径**常泄露作者环境与项目来源：

- 源码里写死的本地开发路径常泄露项目真名与作者环境：`/Users/<作者>/Downloads/<工程目录>/offline-server` → 项目真名 → 对上别处截图／日志里的项目名 → **身份链闭合**
- 记下这些路径，回头和已有的截图/日志/聊天记录交叉比对
- **比路径更硬的一条：commit author email**。`commits?per_page=100` 每条都带 `commit.author.email`，作者常直接把 QQ 号／常用邮箱填进去——**邮箱串 ＝ GitHub 账号 ←→ 真人平台号的直连**，属于「接口原始字段」，与自认、群资料卡、他人指认不在一个量级，一条全量提交就能把身份链闭合：
  ```bash
  curl -s "https://api.github.com/repos/{o}/{r}/commits?per_page=100" \
    | python3 -c "import json,sys;[print(c['commit']['author']['date'],c['commit']['author']['email'],c['commit']['message'].splitlines()[0]) for c in json.load(sys.stdin)]"
  ```
  同一账号若还 fork 了上游项目，把 `users/{login}/repos` 一并拉下来——**fork 时间点**能证明「照抄/仿照上游」的自述哪一半是真的。
- **GitHub 时间一律 UTC（尾缀 `Z`）**：`created_at`／`pushed_at`／`commit.author.date` 直接和用户口述的日期对，会差一天——17:18Z 的建仓在 +8 就是**次日 01:18**。对日期先 +8 再判；用户给的日子与 UTC 差一天时，先怀疑时区，再怀疑人记错。顺手把「建仓 → 提交 → release → 此后零推送」的时刻一起落档：**「发布即冻结／不再维护」要用 `pushed_at` 停在发布当夜来兑现**，只转述当事人那句「不再维护」不算实证。
- **公开仓 ≠ 线上正在跑的那一套**：私服／社区服的公开仓多是某一夜的快照，线上早改过。判据是**端点集对不上**——公开版自带的 `/health`、`/serverstate` 线上 404，线上多出来的 `/api/quiz`、`/api/register` 仓里根本没有；`/serverlist` 应答里的名字（`Local` vs 配置里的「离线研究服」）也能一眼分开。落档口径写死两段：**公开仓证明「这条路线的起点」，不证明线上程序**；再补一句「开源部分**不含**哪些功能」（门禁／题库／绑号／公告页），别让读者以为整套都放出去了。

### ⑥ 对照旧判断，修正要留痕

新证据推翻旧定性的，档案里必须写明「XX 定性降权/修正」，**不能静默改**——否则后人读档案不知道判断曾经错过。

实操：**保留原判断原文，紧跟一段 ⚠️ 修正注（改判内容 ＋ 依据 ＋ 日期）**，不要直接改写原句——对账时两条都要读得到。被用户或他圈内朋友的一句话推翻时（例如「这东西一眼有问题」）同样适用：先复核、再改判留痕。**改判要回写到所有下游文件**：同一判断常被多个文件引用（一页汇总 ＋ 全量档案里的对应小节 ＋ 事件索引），只改一处 ⇒ 别处还挂着旧结论，每处都留 ⚠️ 修正注并互相指路。

**取证索引本身也会标错——用 sha256 反查**：同一哈希出现在两行，就有一行的文件名是错的（实测「官网首页截图」与「题库截图」同哈希，被标错的那张直接让「手里有原图」这条判断作废）。规则：索引勘误**只增不改**——原行保留，另开「误标更正」节写「位置｜原标｜实为｜判据」，并回写所有引用过该件的结论（凡写过「有 X 原件」的都要重核一次）。**先跑一遍摘要再去调原件**，比逐张看图快得多。同一类错误在本 skill 里成族出现：**「看起来专业／很深」不能当任何身份判据**（见最高铁律与 `references/service-attribution.md` 门禁一节）。

**给判断分档，别一句一档都当定论**：调查档里每条结论标证据级别——**硬证**（接口／画面／本人原话，不可辩）／**强推**（多源交叉，可下结论但写明风险点）／**弱推**（单点或语境，只能记「推断」）／**作废**（被推翻的旧说，留痕禁再引用）。周期性把全表过一遍，比临时想起来查更靠谱；用户问「还有什么没挖出来」时，直接给「待重核清单」而不是凭印象补料。

**定性词要过三源门槛**：`蹭`／`骗子`／`卖整合包`／`盗号` 这类词，除非三个独立源指向同一结论，否则只写事实不写定性。原因不是求稳，是**首份结论大概率会被用户转发进当事群或评论区**——一个未经验证的定性会变成对方的反击起手式，而撤回成本远高于晚说一句。同样口径：**风险要写具体环节**（明文传输／收真实 QQ／改绑不校验／存储不可验证），不写笼统的「会盗号」，后者既站不住也一辩就输。
