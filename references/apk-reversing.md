# APK 逆向分层

> 从 SKILL.md 拆出（2026-09-04 拆薄）。调查对象是 APK 时先看这张表。

| 层 | 做什么 | 工具 | 难度 |
|:--|:--|:--|:--|
| 解包 | 拿资源/文件（APK 本质是 zip） | unzip | 简单 |
| 看代码 | dex → Java 源码 | jadx | 入门（混淆后是耐力活） |
| 重打包 | 改完再签 | apktool + apksigner | 中（v2 签名改字节必炸） |
| 脱壳 | 对付加固壳 | frida/BlackDex/Youpk… | 玄学，无固定流程 |

**调查别人项目的魔改包时，多数情况 clone 源码比拆 APK 更快更有信息量——先看有没有开源，再决定拆包。**

## 外来样本：先隔离，再只读静态检查

用户把**从对方分发渠道取回的本体**（客户端 APK／教程录像／说明文本）放进案件目录并说「隔离处理」时，按这四步走：

1. **本体移出档案目录** → `workspace/quarantine/<YYYYMMDD>-<案子>-样本/`，隔离区自带 「README.md」（清单＋哈希＋处置口径＋结论摘要）；**案件档案里只留哈希与结论**。
2. **根 `.gitignore` 加 `workspace/quarantine/`** — 这类本体动辄几百 MB，默认不受任何 ignore 规则保护（实测几个 APK 以 `??` 裸奔在 `git status`），下一次 `git add` 就把它们塞进仓库。
3. **不安装、不运行、不联机、不外传**；对外只给哈希。检查用 `scripts/apkscan.py`（纯标准库，只读）。
4. **不下「是否含恶意代码」的结论**——只读字符串／清单检查 ≠ 行为分析，报告末尾写明「本次只做只读检查，未做行为分析」。

**只读静态检查能拿到的硬结论（没有 aapt／jadx 也够）**：

| 项 | 怎么取 | 判什么 |
|:--|:--|:--|
| 包名 ＋ 权限 ＋ 版本 ＋ 应用名 | `AndroidManifest.xml` 是二进制 XML：**用 `scripts/axml_probe.py <样本.apk>` 解析**（纯标准库） | **包名沿用了谁的命名空间**——比「协议同构」更硬的一手（实测客户端包名与上游开源离线项目同名 ⇒ 直接坐实重打包）；`label`（应用名被改成运营方品牌）／`debuggable`／`usesCleartextTraffic`／`versionName` 一并读出；权限清单拿去与「教程要求开的权限」对照 |
| ~~包名/权限（旧法）~~ | ~~正则抽 UTF-16LE 可打印串（`(?:[\x20-\x7e]\x00){4,}`）~~ | ⚠️ **已废——粗抽会漏读**：实测同一个 manifest 只捞到 2 条权限，实际 6 条（含读写外部存储），照它写「只要两权限」就是错结论。粗抽只能当找不到解析器时的保底，且结论里要标「可能不全」 |
| 签名 | `META-INF/*.RSA` 落盘 → `openssl pkcs7 -inform DER -print_certs -noout` 读 `subject=`；再在文件尾 2MB 内搜 `APK Sig Block 42` | 主体 `CN=Android Debug` ＋ 无 v2/v3 块 ⇒ **重打包自签**（改包者痕迹） |
| 内嵌地址 | 逐条目抽 `https?://…` | 对外的 `域名:端口` ＋ **打包者内网地址**（`192.168.*`／`10.*`）——后者是打包者环境指纹，交付时单独列 |
| 上游／官方残留 | 同上 | 官方 SDK／支付端点／上游库名还在 ⇒ 基线是「官方客户端或上游包改的」 |

- ⚠️ **包名不一定以 `com`/`cn`/`net`/`org` 开头**（实测第三方工具是 `bin.mt.plus`）——别用前缀白名单过滤，否则真正的包名被滤掉，只剩 manifest 里被引用的别的包。
- ⚠️ **脚本输出要落文件，别管进 `head`／`tail`**：管道提前关闭会让脚本在写报告前被 SIGPIPE 杀掉，报告没落盘＝白跑一轮。先落盘再 `cat`。
- **教程录像能交叉验证包名**：解压目标目录就是客户端的 `Android/data/<包名>/`，帧上读一次即得，与 manifest 互证。

## 拆包第二层：Java 层动没动／业务层有没有自建痕迹

只读静态检查过了第一层（包名/签名/地址）之后，若还要回答「**改动到底在哪一层**」，按四格走：

| 看什么 | 怎么取 | 判什么 |
|:--|:--|:--|
| **Java 层有没有动过** | 解出 `classes.dex` → 正则 `L(com\|cn\|net\|org\|bin)/[A-Za-z0-9_/$]+;` 数**顶层包直方图** | 全是第三方 SDK（支付／登录／引擎运行时／官方前端组件）⇒ **改动不在 Java 层**，包名只作为应用标识存在 |
| **业务/引擎元数据有没有自建痕迹** | `assets/bin/Data/Managed/Metadata/global-metadata.dat`、`lib/*/libil2cpp.so` 做**关键词＋上下文**检索（自研名／运营方品牌名／口令词／内网 IP） | 命中若全是官方系统名（`NoticeHelper`、`OfflineTime`…）⇒ 元数据也是官方原样，改动只在资源与配置层 |
| **native 库清单** | `namelist()` 里 `lib/` 下的 `.so` | 与上游方案对照：上游若是「注入 `libX.so` ＋ `System.loadLibrary("X")`」而样本里没有 ⇒ **不是那套方案**，只是改了配置直连 |
| **工序残留** | 条目名正则筛 `orig\|bak\|backup\|decrypted` | `.orig`＝改前版（白送 diff）；`*_decrypted` 与加密件并存 ⇒ 解密→改→重打包的痕迹（改前/改后两版**逐字节入档**再 diff） |

⚠️ **关键词检索的两个翻车点**（都会直接产出错结论）：

1. **大小写／子串会撞车**：`doall` 在某 il2cpp 元数据里 4 处命中**全是 `DoAllTrue`**（PlayMaker 动作名）。只判「有没有命中」就会写成「客户端里带这个口令」——**每条命中都要看上下文再定性**。
2. **「零命中」要立得住，先证明「能搜到」**：先确认目标文件是**明文／可索引**（拿一个已知串验证能命中），否则加密或打包会让零命中变成假结论。

**结论写法**：分三层落笔——「Java 层＝官方原样／业务元数据层＝官方原样／资源与配置层＝改了哪几个键」＋「应用名/包名改成什么」。这样一句话说清重打包改了哪一层，比一堆字符串命中清单有用得多。

## 官方原包对照：把「改了什么」钉死（用户手上有正版包时最硬的一步）

用户说「这是正统的包，一直在手机里」时，别只拿它对图标——**两份 APK 逐条对照**能把改动面做成清单，比任何「协议同构／包名沿用」的推断都硬。步骤：

1. **身份三行**：`scripts/axml_probe.py` 读包名／版本／label，`META-INF/*.RSA` 读签名主体 ⇒ 官方包＝渠道签名（`BILIGAME.RSA` 类，`subject=O=<渠道名>`），改包＝`CN=Android Debug` 自签。⚠️ **改包者常照抄官方的 versionName/Code**（实测两份同版本号）⇒ 版本号分不出两份，判据只能落在包名／签名／条目差异上。
2. **逐条对照**：把两边 `zip` 条目按 `(name, size, CRC)` 归成四类——只在官方／只在改包／共有且相同／共有且不同。
   - ⚠️ **「共有但不同」的计数会被重打包工具链虚增**：官方资源目录带版本后缀（`res/drawable-hdpi-v4/`），重打包后成 `res/drawable-hdpi/`，同一批资源同名不同路径、XML／9-patch 也被重编译 ⇒ 实测几百条「不同」里大部分只是工具链差异。**别把「不同」一律读成「被改」**，实质改动以第 3 步的关键文件 hash 与「只在一方」的清单为准。
   - ⚠️ **尺寸差不是改动量**：某 native 库两份只差 936 字节，逐字节比对却是 **620,869 段／26.9 MB 不同**（构建/加壳会让整段重排）⇒ 报「改了多少」只认**逐字节比对结果**，尺寸差只当线索；同时 **「只在一方存在」的条数比「共有里多少条不同」更能支撑结论**（后者被重编译灌满噪声）。
3. **关键文件 hash 对照表**（一列官方、一列改包）：SDK 配置／资源包／渠道号／加密资源／图标——**同 hash ⇒ 原样未动**，这份「未动清单」和改动清单一样是结论（证明改动是定点而不是换皮）；不同 ⇒ 逐个说清改了什么。
4. **三方归类成「改动清单」**：① **改**（共有里 hash 变了的）② **删**（只在官方包里的，如安全／加固 `.so` 被移除）③ **加**（只在改包里的——**改包者新增了官方包根本没有的东西**，如明文源码／自建 bundle，属独立一类证据）。三类各成一行。
5. **配置三点对齐**：官方原件 → 改包里的 `.orig` 中间态 → 改包现版。有官方基准才数得清「改了几轮」，也才判得出 `.orig` 到底是官方原件还是更早的中间态（两种都出现过：一个 `.orig` 与官方件逐字节相同，另一个 `.orig` 已是改过一版的中间态）。
6. **边界**：改包里若没有任何上游标识，「哪一步是谁做的」判不出 ⇒ 只主张「**该客户端是在官方包上改的**」，不指认改动者；新增文件的**加入者与时点**记未决。
7. **顺手保样本**：用户从手机／聊天记录递来的官方包常落在会被清理的 `cache/` 下——**复制一份进隔离区**（本体不入 git，档案里只留路径与 hash）。

## 官方原包对照 · 第二层（逐条四分类之后还该看的三块）

逐条分类做完，改动清单通常只到「包名／签名／安全库／配置／图标／新增明文源码」这一档。再往下有三块能明显加长清单，而且全是纯只读：

| 块 | 怎么取 | 能钉死什么 |
|:--|:--|:--|
| **打包方式** | 逐条目统计 `compress_type`（deflate=8／stored=0）以及 `file_size` vs `compress_size`，按顶层目录汇总 | **体积差常常是存储方式而不是内容**：实测改包把 `lib/*.so` 全改成未压缩，APK 从 154 MB 变 307 MB，内容只多十几 MB ⇒ **报体积必须同时报压缩方式**，否则「体积翻倍」会被读成「内容翻倍」 |
| **资源清单文件**（`assets/version.data`、`*.list`、`pack` 索引这类） | 头几个 `u32`（版本号／条目数／第二计数）＋全量路径串集合差 | 条目数直接给出「**资源面是否晚于官方该版本**」的硬结论；新增项里出现官方后期活动的资源名即坐实；**「删 0 条」和新增一样是结论** |
| **manifest 量化指标** | `axml_probe.py` 读字符串池条数／权限集合／`application` 入口／`debuggable`／`allowBackup`／`usesCleartextTraffic` | 字符串池骤降（228→89）＋权限被砍（10→6，砍的全是设备标识／渠道归因类）＋**官方 SDK 的 `application` 入口被剥掉**＝渠道 SDK 被剥离的量化证据；`usesCleartextTraffic` 由无到有 ⇒ **与「站点无 HTTPS／明文传凭据」在客户端层咬合**，是把两份材料串起来的一条硬证 |

⚠️ **字符串集合差先裁剪再比**：这类清单里的路径是**长度前缀＋载荷**，直接 `[\x20-\x7e]{6,}` 抓会把后继字节当路径尾巴（同一路径出现多个变体）⇒ 集合差虚高（实测虚高成「新增 889／移除 437」，而裁剪到扩展名收尾后是**新增 345／移除 0**，后者才是事实）。裁法：正则限定以已知扩展名收尾，如 `[A-Za-z0-9_!\-/]+\.(u|png|pack|bin|json)`。

⚠️ **`.u`／bundle 类资源先判格式再谈加密**：`UnityFS\0` 开头＝标准 Unity AssetBundle（未加密，只是带压缩块）；改包里的 `*_decrypted` 若与原件**同尺寸**、且逐字节差异是**每段 2 字节对调**，那只是 16 位字节互换 ⇒ 结论写「按字节序变换处理过」，**别写成「解密了加密资源」**。

⭐ **改包里的 `_*_bundle.bin` 这类裸数据文件：拿它跟官方容器的「解压后数据」比哈希**。实测改包内一个 bundle 与官方 `.u` 解出后的裸数据**逐字节相同**（sha256 相等）⇒ 直接坐实「**官方资源被解开后另存／重装**」；这一条比任何"看起来像官方素材"的推断都硬，且顺带解释了那些 bundle 的来历。

**改动清单要写成可增补的表**：逐层对照会不断加行（实测从 6 项长到 10 项），每行标**证据强度**（manifest 解析／逐字节 hash／尺寸差线索），旧层结论被新层推翻时按 SKILL.md ⑥ 回写全部下游文件（导航表／时间轴／判词附件／取证清单四处都要跟上）。

## 图标与视觉资产面（第一层检查别漏了图标）

`res/mipmap-{ldpi,mdpi,hdpi,xhdpi,xxhdpi,xxxhdpi}/app_icon.png`（＋`app_icon_round.png`）是**必看项**——图标是运营方自己做的门面，一眼能分出「官方图标」还是「自制裁切」：

| 看什么 | 判什么 |
|:--|:--|
| 图标画面（交给 `vision_analyze`，问法里要求「逐字写出图上文字」） | 官方图标＝完整 logo／游戏名排版；**自制＝紧裁的角色特写＋自压一条黑带白字（服务名）**，没有角标／厂商标 |
| `app_icon.png` 与 `app_icon_round.png` 是否逐字节相同（比 sha256） | **相同 ⇒ 没做圆形／自适应图标**（重打包图省事的痕迹之一） |
| 图标 PNG 的 `tEXt`／`tIME` 元数据 | **全无 ⇒ 重新导出／加工过**；官方素材常留着 `date:create` ＋ `Software: Adobe ImageReady`（读法见 `service-attribution.md` §素材与素材元数据） |
| 与运营方**其他公开头像**交叉比对（如群资料截图里的群头像） | 同构图、同角色、**只换底部字样** ⇒ 坐实「**同一套自制视觉资产**」，把「客户端／社群／站点」串成同一条品牌线 |

**图标／头像上的品牌字样是域名线索**：底部那种 `GUGUSJ`／`GUGU.ST` 类字样直接当域名查（`bin/srvrecon <字样>`）。**查不到就写负结果**——「DNS 零记录／CT 零证书／RDAP 无服务 ⇒ **当前不是活域名**」，**不写成「他的另一个域名」**：未注册、已过期、纯装饰字样本机分不出，挂成盯点即可。
